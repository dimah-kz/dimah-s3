---
title: Delete
description: Confirm-first or one-shot delete.
---

`requestDelete` marks a key pending. `confirmDelete` sends the request.
[Delete Button](/docs/react/ui/components/delete-button) takes the same
`useDelete` return as `delete`. Headless callers that already confirmed can
call `remove(key)` instead.

The route name must have `delete` enabled. Keys from an upload live on
that upload route — enable `delete` there rather than adding a second
route for the same prefix
([combining features](/docs/server/routes#combining-features)).

**Flow:** `requestDelete` → your confirm UI → `confirmDelete` (or
`cancelDelete`). Or `remove(key)` in one step.

```tsx
"use client";

import { useDelete } from "@dimah-s3/react";

export function DeleteFile() {
  const { pendingKey, requestDelete, confirmDelete, cancelDelete } = useDelete({
    route: "uploads",
  });
  const storedKey = "uploads/11111111-1111-1111-1111-111111111111/photo.jpg";

  if (pendingKey) {
    return (
      <div>
        <p>Delete {pendingKey}?</p>
        <button type="button" onClick={() => void confirmDelete()}>
          Confirm
        </button>
        <button type="button" onClick={cancelDelete}>
          Cancel
        </button>
      </div>
    );
  }

  return (
    <button type="button" onClick={() => requestDelete(storedKey)}>
      Delete
    </button>
  );
}
```

No dialog? Call `remove`. Several keys? Call `removeMany` (`POST /delete/batch`).

```ts
const { remove, removeMany } = useDelete({ route: "uploads" });
await remove(storedKey);
await removeMany([storedKey, otherKey]);
```

Wire `onSuccess` to keep your own database in sync. Server-side auth belongs
in [`delete.guard`](/docs/server/hooks/delete).

`isConfirming` is `true` while a key is awaiting the dialog
(`phase === "confirming"`). `isDeleting` is `true` while the request is in
flight. `isPending` is either.
