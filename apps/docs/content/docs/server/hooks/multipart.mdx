title: Multipart Hooks
description: Upload large files in parts, with a server-chosen part layout, per-part authorization, checksums, and resumable tickets.
---

Multipart uploads send a large file in parts, in parallel, and can resume
after a failure. Turn them on for a route with `upload.multipart: true`, or
pass a `MultipartConfig` to tune the part size and authorize each call.

```ts title="lib/s3.ts"
import { dimahS3, route } from "@dimah-s3/server";
import { awsS3 } from "./aws-s3";

export const s3 = dimahS3({
  client: awsS3,
  bucket: process.env.S3_BUCKET!,
  routes: {
    video: route({
      upload: {
        fileTypes: ["video/*"],
        maxFileSize: 500 * 1024 * 1024, // 500 MB
        multipart: true, // [!code ++]
        onConfirmed: async ({ key, object }) => {
          // Runs once multipart complete has verified the object.
        },
      },
    }),
  },
});
```

On these routes the React client uploads files of 50 MiB or more in parts
(`DEFAULT_MULTIPART_THRESHOLD`), and smaller files in one request. Complete
runs the same checks and hooks as a single-shot confirm.

Turn multipart on for files over 5 GiB: S3 takes at most that in one PUT or
POST, so a larger single upload returns `FILE_TOO_LARGE`.

## Multipart lifecycle

/>

| Call       | `operation`             | What the server does                                                                                            |
| ---------- | ----------------------- | --------------------------------------------------------------------------------------------------------------- |
| Init       | —                       | Runs `upload.object`, picks the part layout, runs `upload.guard`, creates the upload, and runs `upload.onStart` |
| Sign part  | `"multipart.signPart"`  | Runs `multipart.guard` with the `partNumber` and its `size`, then signs a PUT URL for exactly that size         |
| List parts | `"multipart.listParts"` | Returns the parts S3 already has, so a client can resume                                                        |
| Complete   | `"multipart.complete"`  | Checks every part, assembles the object, reads it with HeadObject, and runs `confirmGuard` and `onConfirmed`    |
| Abort      | `"multipart.abort"`     | Aborts the upload and runs `multipart.onAbort`                                                                  |

- Init returns the `uploadId`, an [upload ticket](/docs/server/upload-tickets),
  `partSize`, `partCount`, and whether parts need a checksum. Every later call
  sends only the ticket.
- The route guard runs on every call. `multipart.guard` runs on the four calls
  after init.
- If `onStart` throws, the upload is aborted.
- On complete, a rejected object is deleted and runs
  [`onRejected`](/docs/server/hooks/upload#when-an-upload-is-rejected).
- Abort is idempotent: an upload that is already gone succeeds and still runs
  `onAbort`. An upload that was completed fails with `409 CONFLICT`.

## Authorize parts

`multipart.guard` gets one context for four calls. Narrow on `operation`;
narrowing to `"multipart.signPart"` also types `partNumber` and `size`.

```ts
import { s3Error } from "@dimah-s3/server";

upload: {
  multipart: {
    guard: (context) => {
      if (context.operation === "multipart.complete" && !context.locals.userId) {
        throw s3Error("UNAUTHORIZED");
      }
      if (context.operation === "multipart.signPart") {
        console.log(context.partNumber, context.size);
      }
    },
  },
},
```

## Part layout

The server picks the layout at init from the declared size, and the client
follows it.

- `partSize` starts at `multipart.partSize`, 8 MiB by default.
- It grows when the file would need more than 10,000 parts, rounds up to a
  whole MiB, and stays between 5 MiB and 5 GiB.
- Every part but the last is exactly `partSize`; the last holds the rest.
- Files over 5 TiB return `FILE_TOO_LARGE`.

```ts
upload: {
  multipart: {
    partSize: 16 * 1024 * 1024, // [!code ++]
  },
},
```

Init checks the declared size against `upload.maxFileSize`. Sign part and
complete enforce the layout:

| Check                                         | Error                    |
| --------------------------------------------- | ------------------------ |
| Sign part: part number outside `1..partCount` | `MULTIPART_PART_INVALID` |
| Complete: a part in `1..partCount` is missing | `MULTIPART_PART_MISSING` |
| Complete: a part is not its layout size       | `UPLOAD_SIZE_MISMATCH`   |
| Complete: checksums on, a part has no SHA-256 | `CHECKSUM_REQUIRED`      |

## Part checksums

With `upload.checksum` or `upload.verifyContent` on, every part sends its
SHA-256 to sign part, and the server signs it into the part URL. S3 rejects a
part whose bytes do not match. The React client hashes each part as it
streams.

## Retries and duplicates

Complete is safe to retry. When an earlier call already completed the upload,
the server verifies the stored object and runs the hooks again, as long as the
object carries this upload's marker. So, as with confirm, `onConfirmed` runs
at least once: dedupe on `uploadToken`.

## Abandoned uploads

A multipart ticket is valid for one day by default, and abort accepts it for
7 more days ([Lifetime](/docs/server/upload-tickets#lifetime)). Parts of an
upload that nobody completes or aborts stay in the bucket, and you pay for
them: add an S3 lifecycle rule that aborts incomplete multipart uploads.

## API Reference

### MultipartConfig

Pass it as `upload.multipart`, or pass `true` for the defaults.

| Prop              | Type                                      | Default           | Description                                                      |
| ----------------- | ----------------------------------------- | ----------------- | ---------------------------------------------------------------- |
| `partSize`        | `number`                                  | `8388608` (8 MiB) | Preferred part size in bytes. Raised for files over 10,000 parts |
| `ticketExpiresIn` | `number`                                  | `86400`           | Seconds a ticket stays valid. Abort accepts it for 7 more days   |
| `guard`           | `(context: MultipartGuardContext) => …`   | —                 | Authorizes sign part, list parts, complete, and abort            |
| `onAbort`         | `(context: MultipartOnAbortContext) => …` | —                 | Runs after an abort                                              |

### multipart.guard

`MultipartGuardContext`. It has `request`, `operation`, `locals`, and `route`
from the [guard context](/docs/server/hooks/global-guard#api-reference), plus:

| Property      | Type         | Description                                                     |
| ------------- | ------------ | --------------------------------------------------------------- |
| `key`         | `string`     | The object key                                                  |
| `bucket`      | `string`     | Target bucket                                                   |
| `uploadId`    | `string`     | The S3 multipart upload id                                      |
| `uploadToken` | `string`     | Stable id of this upload                                        |
| `file`        | `UploadFile` | The file declared at init: `{ name, size, type? }`              |
| `partNumber`  | `number`     | 1-based part number. `"multipart.signPart"` only                |
| `size`        | `number`     | Byte size signed into the part URL. `"multipart.signPart"` only |

### multipart.onAbort

`MultipartOnAbortContext`: the same properties as `multipart.guard`, without
`partNumber` and `size`.

Init uses `upload.guard` and `upload.onStart`, with `uploadId` set. See
[Upload Hooks](/docs/server/hooks/upload#api-reference).
