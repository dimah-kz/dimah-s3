File tools cover different layers: upload UI, managed storage, or the server
policy around an object for its whole life. dimah-s3 is the last kind: upload,
verified confirm, download, and delete on an S3-compatible bucket you own.

| Choose            | When you want                                                                                      |
| ----------------- | -------------------------------------------------------------------------------------------------- |
| **dimah-s3**      | Upload, verified confirm, download, delete, and optional database records, on a bucket you control |
| **Better Upload** | A smaller, upload-focused toolkit on a bucket you control                                          |
| **UploadThing**   | Managed storage and delivery, with no bucket to run                                                |
| **Uppy**          | A broad client-side uploader ecosystem on top of your own backend                                  |

## Feature comparison

| Capability                | dimah-s3                         | [Better Upload](https://better-upload.com) | [UploadThing](https://uploadthing.com) | [Uppy](https://uppy.io)     |
| ------------------------- | -------------------------------- | ------------------------------------------ | -------------------------------------- | --------------------------- |
| **Product model**         | Lifecycle toolkit                | Upload toolkit                             | Managed file service                   | Client uploader             |
| **Storage**               | Your S3-compatible bucket        | Your S3-compatible bucket                  | Managed storage and CDN                | Your bucket or service      |
| **Server policy**         | Named lifecycle routes           | Upload routes + S3 helpers                 | Managed file routes                    | Bring your own or Companion |
| **After upload**          | Signed ticket + `HeadObject`     | Client event; app verification             | Managed completion callback            | Your backend                |
| **Download**              | Signed URL or proxy + React API  | Server helpers                             | Public or signed managed URLs          | Your application            |
| **Delete**                | Guarded route + bulk + React API | Server helpers                             | Hosted API                             | Your application            |
| **Multipart and resume**  | Multipart + persistent store     | Multipart + retries                        | Managed pause/resume                   | S3 multipart or Tus         |
| **Ownership and records** | Optional `@dimah-s3/db`          | Your application                           | Service records + app auth             | Your application            |
| **React UI**              | Headless + optional shadcn       | Hooks + shadcn upload UI                   | Components + hooks                     | Headless core + Dashboard   |
| **Cost and operations**   | Cloud + application operations   | Cloud + application operations             | Managed plan + usage                   | Backend + destination costs |

The table shows what each tool ships, not what you can build on top of it.

## dimah-s3 or Better Upload?

Both upload straight to an S3-compatible bucket you own. Better Upload fits
when the upload is the whole job: concise routes, React hooks, shadcn
components, automatic multipart, and S3 helpers.

Choose dimah-s3 when the app also needs:

- **Verified confirmation.** Confirm accepts only a signed upload ticket, so
  it finishes only uploads the server started. It reads `HeadObject`, rechecks
  size and type, can check the first bytes against the type, and deletes the
  object when a check or `confirmGuard` rejects it.
- **One policy for the whole lifecycle.** One named route and key namespace
  govern upload, private download, proxy delivery, and server-side delete.
- **Resume after a reload.** An `UploadStore` keeps multipart state. When the
  user picks the same file again, the client reuses the parts already in S3.
- **Optional records.** `@dimah-s3/db` adds scoped ownership, lifecycle state,
  folder listings, and quotas.

## dimah-s3 or UploadThing?

UploadThing fits when you want a managed file backend, with no bucket, IAM
policy, CORS rules, or delivery layer to set up.

Choose dimah-s3 when you need control of storage:

- **Your storage.** Objects stay in your AWS S3, Cloudflare R2, MinIO, or
  other S3-compatible bucket.
- **Your policy.** Authentication, key generation, quotas, and lifecycle hooks
  run in your server.
- **No file-service fee.** You pay your provider for storage and transfer, and
  run the server yourself.

## dimah-s3 or Uppy?

Uppy is not a drop-in replacement for `@dimah-s3/react`. Its S3 plugin
expects its own signing contract, while dimah-s3 uses route names and
server-owned keys. To combine them, write a custom Uppy uploader that
translates the operations without letting the browser choose object keys.

If you only need drag-and-drop UI, use the headless
[`useUpload`](/docs/react/hooks/upload) hook or the
[UI components](/docs/ui) instead.

## Build it yourself

### Raw presigned S3 URLs

The AWS SDK alone is a reasonable choice for one small upload flow. As
requirements grow, you also own confirmation, key isolation, multipart
coordination, retries, download authorization, deletion, client state, and
error contracts. dimah-s3 packages those and leaves the `S3Client` in your
hands.

### React Dropzone

React Dropzone handles file selection and drag-and-drop; it is not an upload
backend. `@dimah-s3/react` uses it for file intake, then adds route
constraints, transfer state, progress, retries, confirmation, and multipart.
Use React Dropzone directly when you only need intake.

## Frequently asked questions

<Accordions>

<Accordion title="Is dimah-s3 a drop-in replacement for Better Upload?">

No. The libraries use different route, hook, and response contracts, so a
migration changes both server and client code.

</Accordion>

<Accordion title="Does Better Upload support multipart uploads?">

Yes. Better Upload can use multipart automatically when a route turns it on.
The dimah-s3 difference is resume after a reload, through `UploadStore`, not
multipart itself.

</Accordion>

<Accordion title="Is UploadThing more expensive than dimah-s3?">

Not always. dimah-s3 has no file-service fee, but you pay for storage,
transfer, compute, and the engineering time to run them. UploadThing bundles
managed infrastructure and support into its price. Compare total cost at your
file sizes, traffic, and regions.

</Accordion>

<Accordion title="Does dimah-s3 replace the AWS SDK?">

No. dimah-s3 owns presigned upload, download, and delete. Keep using the AWS
SDK for app-specific operations such as list, copy, retention, or arbitrary
object tagging.

</Accordion>

</Accordions>
