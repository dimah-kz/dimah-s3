## Server

With the plugin registered, `s3.db.objects` and `s3.db.folders` are
available in your routes, jobs, and scripts. Every method that reads or
writes a scope takes it as the first argument, so they can read any scope.
`objects.find` and `objects.update` address one row by `(bucket, key)`:

```ts
const scope = "user:123";

const reports = await s3.db.folders.create(scope, {
  parentId: null,
  name: "reports",
});
const page = await s3.db.objects.list(scope, {
  folderId: reports.id, // null is the root; omit for every folder
  sort: { field: "updatedAt", direction: "desc" },
  limit: 50,
});
const next = await s3.db.objects.list(scope, {
  folderId: reports.id,
  sort: { field: "updatedAt", direction: "desc" },
  cursor: page.nextCursor,
});

const count = await s3.db.objects.count(scope, { status: "active" });
const usage = await s3.db.objects.usage(scope);
const object = await s3.db.objects.find({ bucket: "my-bucket", key });

const children = await s3.db.folders.children(scope, null);
const folders = await s3.db.folders.count(scope);
```

`list` returns `{ objects, nextCursor, firstPage }`. It defaults to active
rows, 50 per page, newest first. A cursor made under other filters is
ignored, and the listing starts again at the first page (`firstPage` is
then `true`).

With `folderId`, `recursive: true` also covers every folder below it, up to
10,000 folders; at the root (`null`) that is the whole scope. `count` takes
the same filter. `folders.descendants` and `folders.ancestors` say where the
rows of such a listing live:

```ts
const found = await s3.db.objects.list(scope, {
  folderId: reports.id,
  recursive: true,
  search: "invoice",
});
// Folders below `reports` whose name contains "2026", by name
const below = await s3.db.folders.descendants(scope, reports.id, {
  search: "2026",
});
// Every folder from the top level down to each id, in path order
const path = await s3.db.folders.ancestors(
  scope,
  found.objects.flatMap((object) => object.folderId ?? []),
);
```

The stores never call S3, and the upload lifecycle stays with the plugin,
so they have no write besides `update`. To remove a file, use the normal
[delete path](/docs/db/setup#delete-behavior). A move needs a folder that
already exists (`FOLDER_NOT_FOUND`). Renaming or moving a folder rewrites
the cached paths under it and leaves every id as it is. An object already
in the bucket is recorded with [`s3.db.record`](#recording-an-object).

```ts
await s3.db.objects.update(
  { bucket: "my-bucket", key, scope }, // only this scope's row
  { folderId: reports.id, attributes: { starred: true } },
);
await s3.db.folders.update(scope, reports.id, { name: "archive" });
```

### Recording an object

`s3.db.record` writes a row for an object that is already in the bucket: a
copy, an import, or a file another system wrote. It does not copy the bytes
and it does not delete them. The size, type, and eTag come from HeadObject.
The key must sit inside the route namespace (`KEY_INVALID`).

Pass `{ headers }`, `{ request }`, or `{ locals }` the way you call
`s3.api`. The instance guard and the route guard run first, then
`resolveScope` and `authorize`, all with `operation: "record"`. `locals`
seeds the guards. The route's `fileTypes` and `maxFileSize` apply, and so
does the quota. An empty object is `FILE_EMPTY`. A file the route does not
allow, or one that does not fit the quota, is refused and left in the
bucket. Delete it yourself if you do not want the bytes.

Calling `record` again for the same bytes returns the same row. A different
object at that key is `OBJECT_EXISTS`. A row an upload or purge holds is
`CONFLICT`. A deleted row is replaced by a new one. `folderId` must already
exist (`FOLDER_NOT_FOUND`); `null` and `""` are the root. `name` is the
display name, under the rule of an uploaded file name: 1 to 255 UTF-8
bytes, with no control or bidi characters. It defaults to the last segment
of the key, fitted to that rule.

```ts
// Your S3 client. dimah-s3 does not wrap CopyObject.
await s3Client.send(
  new CopyObjectCommand({
    Bucket: bucket,
    Key: key, // inside the route namespace, for example `project-files/…`
    CopySource: `${bucket}/${sourceKey}`,
  }),
);

const copy = await s3.db.record(
  {
    route: "project-files",
    key,
    folderId: reports.id,
    name: "plan (copy).pdf",
  },
  { headers }, // or { request } or { locals }
);
```

## HTTP endpoints

`db()` mounts these endpoints next to the dimah-s3 routes. Each one resolves
the caller's scope from the request and runs `authorize` with the
`operation` shown. Body endpoints accept JSON only.

| Endpoint                | Browser action | `operation`     |
| ----------------------- | -------------- | --------------- |
| `GET /db/objects`       | `listObjects`  | `list`          |
| `GET /db/object`        | `getObject`    | `read`          |
| `PATCH /db/object`      | `updateObject` | `update`        |
| `POST /db/folder`       | `createFolder` | `folder.create` |
| `PATCH /db/folder`      | `updateFolder` | `folder.update` |
| `DELETE /db/folder?id=` | `deleteFolder` | `folder.delete` |

Only the instance `guard` runs on these endpoints. A route `guard` does
not: see [Database Setup](/docs/db/setup#register-the-plugin).

`GET` and `PATCH /db/object` take an optional `bucket`. It defaults to the
only bucket your routes use. When routes use several buckets, `bucket` is
required, and a bucket no route uses is a `VALIDATION_ERROR`.

### Listing

`GET /db/objects` defaults to `status: "active"` and `limit: 50`, and
rejects a `limit` above `100`. Unknown query keys, such as `offset` and
`prefix`, are a `VALIDATION_ERROR` (`400`), and so is `status=purging`:
rows that purge has claimed are never listed.

- `folderId` lists one folder: `""` is the root, and any other value is
  that folder's id. Omit it for a flat list of every folder. A missing id
  is `FOLDER_NOT_FOUND` (`404`). A flat list reads the whole scope, so
  `authorize` sees it as a recursive listing of the root (`folder: null`,
  `recursive: true`).
- `recursive=true`, with `folderId`, also covers every folder below it, up
  to 10,000 folders: objects come from the whole subtree, and `folders`
  holds every folder in it. With `folderId=""` that is the whole scope.
  Without `folderId` it changes nothing. `authorize` sees `recursive: true`.
- `search` keeps rows whose `name` contains the text. Case, accents, and
  look-alike letters (`ي`/`ی`, `ك`/`ک`) do not count, Persian and
  Arabic-Indic digits match `0`–`9`, and `%` and `_` are plain text, the
  same on SQLite, PostgreSQL, and MySQL. Each row stores its name folded
  with `normalizeSearchText` from `@dimah-s3/core` (the `search_name`
  column), and the search text is folded the same way.
- `contentType` is an exact type, or `type/*` for every subtype
  (`image/*`).
- `sort` takes `{ field, direction }`, with `field` set to `createdAt`,
  `updatedAt`, `size`, or `name`. The default is `createdAt`, newest
  first. `name` orders by the folded name that search matches, so case and
  accents do not count, on every database; folders are listed in the same
  order. Ties break on the row id, and rows with no value (a pending row's
  `size`) come last in both directions.
- `usage=true` asks for the scope's `usage` on the first page. Without a
  [quota](#quota) it is left out unless asked, because it reads every row
  of the scope.
- `nextCursor` is `null` on the last page. A cursor made under other
  filters is ignored, and the list starts again at the first page.

The first page also carries `limits`, `usage` (with a quota, or with
`usage=true`), and, when `folderId` is set, `folders` and `trail`, the
folders from the root down to the open one.
`folders` holds the direct child folders, or with `recursive` every folder
below the open one, by name. It has at most 1000, and with `search` only
those whose name contains it, matched like file names. The first page of a
search carries `total`, the objects that match across every page. Every
page of a recursive listing carries `locations`: the folders on the way to
its objects and, on the first page, to `folders`. Walk `parentId` from a
row's `folderId` to say where it lives. The response never names the
caller's scope: it stays on the server.

```ts
const page = await api.db.listObjects({
  folderId: "",
  search: "invoice",
  sort: { field: "size", direction: "desc" },
});
const more = await api.db.listObjects({
  folderId: "",
  search: "invoice",
  sort: { field: "size", direction: "desc" },
  cursor: page.nextCursor ?? undefined,
});

// The open folder and every folder below it
const found = await api.db.listObjects({
  folderId: folder.id,
  recursive: true,
  search: "invoice",
});
found.total; // objects that match, across every page
found.locations; // folders on the way to each row
```

<Callout title="Scope is resolved on the server">
  No browser action takes a scope. The plugin resolves it from the request with
  `resolveScope`. To read another scope, use `s3.db.objects` on the server.
</Callout>

## Folders

Folders are logical: an object's `folderId` and the `storage_folder` table.
They never change the S3 key. Empty folders are listed too. A folder is its
id. Renaming it or moving it changes one row, then rewrites the cached
`path` of that folder and everything inside it. Object rows keep the same
`folderId`.

A folder name is 1 to 255 characters, not `.` or `..`, and has no `/`, no
control characters, and no whitespace at either end. The cached path is at
most 1024 UTF-8 bytes, like an S3 key, and 32 levels deep. Names are
NFC-normalized. Anything else is `FOLDER_INVALID` (`400`). Moving a folder
into itself or into one of its descendants is `FOLDER_INVALID` too. A
sibling with the same name is `FOLDER_EXISTS` (`409`). A missing id is
`FOLDER_NOT_FOUND` (`404`). Two moves that run at once and would put each
folder inside the other end with one of them undone and `CONFLICT`
(`409`). In JSON and in types the root is `null`; on the wire
(`?folderId=`, `clientMetadata.folderId`) it is `""`.

Folders belong to the [scope](/docs/db/setup#scope), not to a route: every
list of one scope shows the same tree.

An upload goes to the folder in `clientMetadata.folderId`. That folder must
already exist. [`dbObjectSource`](#browser) sets it for uploads into the
open folder. With your own `useUpload`, pass the id per call.
`DB_FOLDER_ID_KEY` from `@dimah-s3/db/client` is that key:

```ts
import { DB_FOLDER_ID_KEY } from "@dimah-s3/db/client";

await upload.handleFiles(files, {
  uploadOptions: { clientMetadata: { [DB_FOLDER_ID_KEY]: reports.id } },
});
```

```ts
const reports = await api.db.createFolder({ name: "reports" });
await api.db.createFolder({ parentId: reports.folder.id, name: "2026" });
await api.db.updateFolder({ id: reports.folder.id, name: "archive" });
await api.db.deleteFolder({ id: reports.folder.id });
```

- `createFolder` creates one folder. The parent must already exist. An
  existing name in that parent is `FOLDER_EXISTS` (`409`). With a
  [quota](#quota) that sets `maxFolders`, one folder past the cap is
  `QUOTA_EXCEEDED` (`403`).
- `updateFolder` renames (`name`), moves (`parentId`, `null` is the root),
  or both.
- `deleteFolder` removes an empty folder. A folder with child folders, or
  with active or pending objects, is `FOLDER_NOT_EMPTY` (`409`). A missing
  folder is not an error.

## Update an object

`PATCH /db/object` renames an object, moves it to another folder, or sets
its attributes. Omitted fields stay as they are. Only active objects can be
updated; anything else is `OBJECT_NOT_FOUND`.

```ts
const { object } = await api.db.updateObject({
  key: file.key,
  name: "Q3 report.pdf",
  folderId: reports.id, // null moves it to the root
});
```

`name` follows the rule of an uploaded file name: 1 to 255 UTF-8 bytes,
with no control or bidi characters. A move requires the target folder to
exist. `authorize` sees the folder the object is in as `folder` and
`folderId`, and the target folder as `destination`. Renames and moves
change only the row: the S3 key stays as it is.

## Attributes

Attributes are your own JSON on each row, such as a description or tags.
Enable them with a [Standard Schema](https://standardschema.dev) (Zod,
Valibot, ArkType):

```ts title="lib/s3.ts"
import * as z from "zod";

db({
  client: dimahS3Db,
  resolveScope,
  attributes: {
    schema: z.object({
      description: z.string().max(500).optional(),
      tags: z.array(z.string().max(32)).max(10).optional(),
    }),
  },
});
```

`PATCH /db/object` with `attributes` replaces them after validation:

```ts
await api.db.updateObject({ key: file.key, attributes: { tags: ["q3"] } });
```

- `attributes: null` clears them, without the schema.
- Without `attributes.schema`, a PATCH with `attributes` is a
  `VALIDATION_ERROR`.
- The access check runs first, so a caller without access never reaches
  your schema. Then a schema failure, or attributes larger than `maxBytes`
  as JSON (default 16 KiB), is a `VALIDATION_ERROR` (`400`).
- `toClient` maps the stored attributes to what the browser sees. Without
  it, the browser sees all of them. `authorize` always sees them as stored.

Type the browser side by passing the client attributes to `dbClient`:

```ts
dbClient<{ description?: string; tags?: string[] }>();
```

## Quota

`quota` caps the bytes, files, and folders of a scope (`maxBytes`,
`maxFiles`, `maxFolders`). Pass fixed caps, or a function that returns them
per request (`null` for no cap):

```ts
db({
  client: dimahS3Db,
  getSession,
  resolveScope: ({ session }) => (session ? `user:${session.userId}` : null),
  quota: ({ session }) =>
    session?.plan === "pro"
      ? { maxBytes: 10 * 1024 ** 3 }
      : { maxBytes: 1024 ** 3, maxFiles: 500 },
});
```

The function gets the [scope context](/docs/db/setup#scope) plus the
resolved `scope`. Bytes and files are checked twice:

1. At upload, against the scope's usage: active sizes plus the declared
   sizes of pending uploads that have not expired. The row the upload
   replaces is left out.
2. At confirm, against the verified size from HeadObject. When that fails,
   the server deletes the object and the plugin removes its row. A
   confirm replay is not checked again.

`maxFolders` is checked when `POST /db/folder` creates a folder.

A refusal is `QUOTA_EXCEEDED` (`403`), with `params.limit` set to
`"bytes"`, `"files"`, or `"folders"`.

With a quota, the first page of `GET /db/objects` carries `usage` and
`limits` (the caps for the scope). `dbObjectSource` merges them into the
list's `usage`, so `ObjectListUsage` shows the meter against the server's
caps. Without a quota, `limits` is `null` and `usage` is sent only when the
query asks with `usage: true` (`dbObjectSource(api.db, { usage: true })`).

<Accordions>
<Accordion title="How should I check quotas for a large scope?">

A cap on files alone (`maxFiles`) is one `COUNT`. A byte cap sums every
live row of the scope on each upload and confirm, and `usage` does the
same on each first page. That is fine for demos and light use, but not for
frequent uploads on large scopes. Keep a counter of your own in that case,
and return caps from the `quota` function that account for it.

</Accordion>
</Accordions>

## Browser

Register `dbClient()` once. In a client component, `s3Client.useApi()`
gives you `api.db`:

```ts title="lib/s3-client.ts"
"use client";

import { createS3Client } from "@dimah-s3/react";
import { dbClient } from "@dimah-s3/db/client"; // [!code ++]

export const s3Client = createS3Client({
  basePath: "/api/s3",
  plugins: [dbClient()], // [!code ++]
});
```

`dbObjectSource(api.db, options)` turns those actions into a
[`useObjectList`](/docs/react/hooks/object-list) source:

- Each page lists one folder, and the first page carries its child folders
  and the breadcrumb `trail`. `parent` is a folder id.
- A search is recursive, and `searchScopes` is `["folder", "all"]`:
  `searchScope: "folder"` sends the open folder with `recursive`, and
  `"all"` the root. Each result gets its `location` from `locations`, and
  the first page's `total` becomes the list's `total`. Pass
  `recursiveSearch: false` to search the open folder only, for an
  `authorize` that refuses `recursive`.
- Uploads from the list go to the open folder (`uploadOptions`).
- "New folder" calls `api.db.createFolder`.
- Rename calls `api.db.updateObject` or `api.db.updateFolder` with the new
  `name`. The object key stays. `folders: false` still renames files.
- The list's `search` becomes `search`, and its sort takes `name`, `size`,
  and `updatedAt`.
- The usage line is the scope total with its caps, not the open folder's.
  It shows when the plugin sets a quota, or with `usage: true`.
- `limit` is clamped to the server's range, 1 to 100.

Pass `folders: false` for a flat list with no folder actions. Its search
covers every object of the scope, without search scopes or locations.

```tsx title="components/files.tsx"
"use client";

import { dbObjectSource } from "@dimah-s3/db/client";
import { useObjectList } from "@dimah-s3/react";
import { s3Client } from "@/lib/s3-client";

export function Files() {
  const api = s3Client.useApi();
  const list = useObjectList({
    ...dbObjectSource(api.db, { route: "files" }),
    queryKey: ["files"],
  });

  if (list.isLoading) return <p>Loading…</p>;

  return (
    <ul>
      {list.entries.map((entry) => (
        <li key={entry.key}>{entry.name}</li>
      ))}
      {list.hasMore ? (
        <li>
          <button type="button" onClick={() => void list.loadMore()}>
            More
          </button>
        </li>
      ) : null}
    </ul>
  );
}
```

[`ObjectList`](/docs/react/ui/components/object-list) renders the same
state with folders, upload, and usage: `<ObjectList list={list} />`.
