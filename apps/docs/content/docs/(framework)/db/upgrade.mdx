`@dimah-s3/db` 2.0 beta reads and writes schema `2.1.0`, and that schema is
the only one in the package. It does not upgrade a 1.x database or a
database created at schema `2.0.0`. For the code changes in every package,
see [Upgrade to 2.0 beta](/docs/migration-2-0).

## A new database

Create the tables from [Setup](/docs/db/setup): generate the Drizzle tables
or the Prisma models with `runCli`, or call `migrate(client)` with Kysely.
Point those tools at a new database. An ORM diff against an older database
can drop columns.

A database from an earlier 2.0 beta, including one already at `2.0.0`, is
not migrated. Create schema `2.1.0` on a new database. Folders are rows
with ids: an object stores `folderId`, and renaming or moving a folder
rewrites cached paths without rewriting object rows.

## From the shipped schema files

Earlier betas shipped `@dimah-s3/db/drizzle/<dialect>`, `prisma/`, and
`sql/`. Generate the schema with `runCli` instead, and point your ORM at
the generated file. A database created from the shipped files stays at
`2.1.0`. What the ORM then changes depends on the database.

### PostgreSQL

The text columns become `varchar(n)`. `drizzle-kit` writes
`ALTER COLUMN "scope" SET DATA TYPE varchar(255) USING "scope"::varchar(255)`,
and an explicit cast truncates a longer value instead of failing. Two
scopes that share their first 255 characters would become one. Run this
check first. Each value must fit the limit in its comment:

```sql
SELECT
  max(length("scope")) AS "scope",               -- 255
  max(length("bucket")) AS "bucket",             -- 255
  max(length("key")) AS "key",                   -- 1024
  max(length("route")) AS "route",               -- 255
  max(length("folder_id")) AS "folder_id",       -- 255
  max(length("filename")) AS "filename",         -- 255
  max(length("content_type")) AS "content_type", -- 255
  max(length("e_tag")) AS "e_tag",               -- 255
  max(length("acl")) AS "acl",                   -- 255
  max(length("upload_token")) AS "upload_token"  -- 64
FROM "storage_object";

SELECT
  max(length("scope")) AS "scope",         -- 255
  max(length("parent_id")) AS "parent_id", -- 255
  max(length("name")) AS "name",           -- 255
  max(length("path")) AS "path"            -- 1024
FROM "storage_folder";
```

The change rewrites `storage_object`, `storage_folder`, and their indexes
under an `ACCESS EXCLUSIVE` lock, so reads and writes wait until it ends.
Raising a length later does not rewrite the table.

### SQLite and MySQL

On SQLite, `drizzle-kit` recreates the three tables and copies the rows.
SQLite does not enforce `varchar` lengths, so no value changes. On MySQL,
the tables already match the shipped `sql/mysql.sql`.

### Code that reads the tables

`s3.db.objects` returns the same rows as before. Code that queries the
tables itself sees the generated types:

- `size` and `declaredSize` are `bigint` in JavaScript, not `number`.
  `JSON.stringify` throws on a `bigint`, and so does arithmetic with a
  `number`. Convert with `Number(row.size)`.
- `status` is a `string` and `s3Metadata` is `unknown`, without the
  shipped `$type`.
- `id` has no default. The plugin generates ids, so a row you insert
  yourself needs one.
- The Prisma models are `storageObject` and `storageFolder`, so the Prisma
  Client types follow those names. `prisma.storageObject` is unchanged.

## Timestamps written by Kysely outside UTC

Since beta.8, the Kysely adapter writes and reads timestamps in UTC on
PostgreSQL and MySQL, as Drizzle and Prisma already did. Before, it wrote
the local time of the process. If a Kysely process outside UTC wrote your
rows, they now read shifted by its offset. Rewrite them once, with the zone
that process ran in:

```sql
-- PostgreSQL. Asia/Tehran stands for the zone of that process.
UPDATE "storage_object" SET
  "expires_at" = ("expires_at" AT TIME ZONE 'Asia/Tehran') AT TIME ZONE 'UTC',
  "confirmed_at" = ("confirmed_at" AT TIME ZONE 'Asia/Tehran') AT TIME ZONE 'UTC',
  "created_at" = ("created_at" AT TIME ZONE 'Asia/Tehran') AT TIME ZONE 'UTC',
  "updated_at" = ("updated_at" AT TIME ZONE 'Asia/Tehran') AT TIME ZONE 'UTC',
  "deleted_at" = ("deleted_at" AT TIME ZONE 'Asia/Tehran') AT TIME ZONE 'UTC';

UPDATE "storage_folder" SET
  "created_at" = ("created_at" AT TIME ZONE 'Asia/Tehran') AT TIME ZONE 'UTC',
  "updated_at" = ("updated_at" AT TIME ZONE 'Asia/Tehran') AT TIME ZONE 'UTC';
```

On MySQL, use `CONVERT_TZ(column, '+03:30', '+00:00')` with the offset of
that process. Rows written by Drizzle or Prisma, or by a Kysely process in
UTC, are already right: leave them.

## Check

Call `checkSchema` at startup. It throws unless the database is at
`2.1.0`:

```ts
await s3.db.checkSchema();
```

A database at any other version throws on the first query too.
