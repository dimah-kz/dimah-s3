Add the `db()` plugin to an existing [`dimahS3()`](/docs/server/setup)
server. You need Drizzle, Prisma, or Kysely connected to a database.
[`examples/with-db`](https://github.com/dimah-kz/dimah-s3/tree/v2/examples/with-db)
is a working reference (Next.js, Drizzle, SQLite).

<Callout title="Start from a new database">
  The package reads schema `2.3.0` only. It leaves a 1.x or earlier 2.x database
  as it is: see [Upgrade the schema](/docs/db/upgrade).
</Callout>

### Install [step]

```npm
npm i @dimah-s3/db@beta
```

`@aws-sdk/client-s3` and `@dimah-s3/server` are peers: use the ones your
server already has. Do not install `fumadb`. The adapters ship from
`@dimah-s3/db/adapters/*`.

### Create the database client [step]

Wrap your connection with an adapter, then create the client with
`DimahS3Db.client()`:

<Tabs items={["Drizzle", "Prisma", "Kysely"]}>
<Tab value="Drizzle">

```ts title="lib/dimah-s3-db.ts"
import { DimahS3Db } from "@dimah-s3/db";
import { drizzleAdapter } from "@dimah-s3/db/adapters/drizzle";
import Database from "better-sqlite3";
import { drizzle } from "drizzle-orm/better-sqlite3"; // or your driver
import { relations } from "../db/dimah-s3"; // written by `generate`

export const db = drizzle({ client: new Database("local.db"), relations });

export const dimahS3Db = DimahS3Db.client(
  drizzleAdapter({ db, provider: "sqlite" }), // or "postgresql" | "mysql"
);
```

With tables of your own, build the relations from both:
`defineRelations({ ...appTables, storageObject, storageFolder, private_dimah_s3_settings })`.

</Tab>

```ts title="lib/dimah-s3-db.ts"
import { DimahS3Db } from "@dimah-s3/db";
```

```ts title="lib/dimah-s3-db.ts"
import { kyselyAdapter } from "@dimah-s3/db/adapters/kysely";
```

- `DimahS3Db` is the [FumaDB](https://fumadb.dev) library for this schema.
  Use its client only through `db()` and the functions in these docs: the
  rest follows FumaDB's own versions.
- On PostgreSQL and MySQL the timestamp columns have no time zone. Every
  adapter reads and writes them in UTC, so instances in different zones
  agree on deadlines like `expiresAt`.
- To keep the tables in a PostgreSQL schema, see
  [PostgreSQL schema](#postgresql-schema).

### Register the plugin [step]

Pass `db()` in `plugins`. `getSession` loads the caller, and
[`resolveScope`](#scope) returns a stable owner string for them, or `null`
to reject the call with `UNAUTHORIZED` (`401`):

```ts title="lib/s3.ts"
import { S3Client } from "@aws-sdk/client-s3";
import { db } from "@dimah-s3/db";
import { dimahS3, route } from "@dimah-s3/server";
import { getSession } from "@/lib/auth"; // your auth
import { dimahS3Db } from "@/lib/dimah-s3-db";

const awsS3 = new S3Client({ requestChecksumCalculation: "WHEN_REQUIRED" });

export const s3 = dimahS3({
  client: awsS3,
  bucket: process.env.S3_BUCKET!,
  plugins: [
    db({
      client: dimahS3Db,
      getSession: (request) => getSession(request),
      resolveScope: ({ session }) =>
        session ? `user:${session.userId}` : null,
    }),
  ],
  routes: {
    files: route({
      upload: { maxFileSize: 20 * 1024 * 1024 },
      download: true,
      delete: true,
    }),
  },
});
```

- Set `DIMAH_S3_SECRET` in your environment. `dimahS3()` signs
  [upload tickets](/docs/server/upload-tickets) with it, and `db()` binds
  each ticket to the caller's scope.
- Every route is tracked unless it sets `plugins: { db: false }`
  ([route options](#route-options)).
- The plugin does not turn operations on. Enable download and delete on the
  **same** route as upload when those callers share the objects
  ([combining operations](/docs/server/routes#combining-operations)).

<Callout type="warn" title="Route guards do not run on /db/*">
  The `/db/*` endpoints run only the instance `guard`, with the operation
  `"plugin"`: most of them name no route. Set what `resolveScope` needs, such as
  `locals.userId`, in the instance guard, or read it from `request` and
  `session`.
</Callout>

### Check the schema at startup [step]

Call `checkSchema` on `s3.db` (also `s3.context.db`) to fail fast:

```ts
await s3.db.checkSchema();
```

It throws, with what to run, unless the database is at `2.3.0` and both
tables can be read. Without this call, the first query runs the same check.

### Register the client plugin [step]

For listings and folders in the browser, add `dbClient()` to the React
client:

```ts title="lib/s3-client.ts"
"use client";

import { createS3Client } from "@dimah-s3/react";
import { dbClient } from "@dimah-s3/db/client"; // [!code ++]

export const s3Client = createS3Client({
  basePath: "/api/s3",
  plugins: [dbClient()], // [!code ++]
});
```

Under `s3Client.Provider` ([React setup](/docs/react/setup)),
`s3Client.useApi().db` holds the [browser actions](/docs/db/api#browser).

## Scope

Every row belongs to a scope, such as `user:123` or `org:acme`, that
`resolveScope` returns for the caller:

- It sees who is calling, never the target object, so one caller gets the
  same scope when an upload ticket is bound, used, and confirmed. Checks on
  the target belong in [`authorize`](#authorize).
- A scope is 1 to 255 characters, with no whitespace at either end. Anything
  else fails the call as a config error (`500` `INTERNAL_ERROR`, with the
  reason in the server log) before any row is written.
- Folders belong to the scope, not to a route. Every list of one scope shows
  the same folder tree, and a folder can hold objects of several routes.
  Give callers separate scopes for separate trees.
- To share objects between users, resolve them to the same scope, such as
  `org:acme`.
- `getSession` runs at most once per `Request`. `resolveScope` runs once per
  call, operation, and route, so two `s3.api` calls that share a `Request`
  but pass different `locals` resolve separately.

`resolveScope` receives a [`ScopeContext`](#scopecontext). Its `operation`
says what the call does:

| `operation`     | Runs for                                            |
| --------------- | --------------------------------------------------- |
| `upload`        | presign, multipart init, and `s3.put`               |
| `confirm`       | confirm, and the confirm step of multipart complete |
| `multipart`     | part, list, abort, and complete                     |
| `download`      | presigned download and `GET /file`                  |
| `delete`        | delete, and each key of `deleteMany`                |
| `list`          | `GET /db/objects`                                   |
| `read`          | `GET /db/object`                                    |
| `update`        | `PATCH /db/object`                                  |
| `folder.create` | `POST /db/folder`                                   |
| `folder.update` | `PATCH /db/folder`, a rename or a move              |
| `folder.delete` | `DELETE /db/folder`                                 |
| `record`        | `s3.db.record`                                      |

## Authorize

`authorize` narrows access after the ownership check. Return `false` to
reject the call with `FORBIDDEN` (`403`):

```ts title="lib/s3.ts"
const inArchive = (path?: string | null) =>
  path === "archive" || path?.startsWith("archive/") === true;

db({
  client: dimahS3Db,
  getSession,
  resolveScope: ({ session }) => (session ? `user:${session.userId}` : null),
  // `archive/` is read-only: nothing in it changes, and nothing moves in.
  authorize: ({ operation, folder, destination }) => {
    if (["list", "read", "download"].includes(operation)) return true;
    return !inArchive(folder) && !inArchive(destination?.folder);
  },
});
```

`folder` covers a rename, a delete, and a move out of the archive, and a
rename or delete of the archive folder itself. `destination` covers a move
into it and a new folder inside it.

Ownership runs first, and `authorize` cannot widen it:

- A row belongs to the scope that wrote it. A caller from another scope gets
  `OBJECT_NOT_FOUND` (`404`), the same as for a key with no row, so nobody
  learns which keys other scopes hold.
- An upload to a key another scope holds gets `FORBIDDEN`: upload keys are
  the server's choice.

`authorize` receives an [`AuthorizeContext`](#authorizecontext). Its
`object` is the stored row when the call targets one (confirm, the multipart
calls, download, delete, read, and update): the server view, with `scope`,
`s3Metadata`, and the stored attributes, not the `attributes.toClient`
output.

### Folder and destination

`folder` and `folderId` say where the target is now, and `destination` where
the call puts it:

| Call                           | `folder` / `folderId`       | `destination`                              |
| ------------------------------ | --------------------------- | ------------------------------------------ |
| Download, delete, read, rename | the folder the object is in | none                                       |
| Object move (`PATCH`)          | the folder the object is in | the folder it moves into                   |
| Upload, `s3.db.record`         | the folder it goes into     | none                                       |
| `list`                         | the folder it opens         | none                                       |
| `folder.create`                | the parent folder           | the new path, and the parent's id          |
| `folder.update`                | the folder as it is         | its new path, and the id of its new parent |
| `folder.delete`                | the folder                  | none                                       |

- For a stored object, both come from its row, whatever the request names,
  so a rule on `folder` holds for downloads, deletes, and renames too. When
  the object's folder no longer exists, `folderId` is set and `folder` is
  left out.
- An upload on a `replace: "overwrite"` route that replaces an active object
  gets that object as `object`, and its folder as `folder`, not the folder
  in `clientMetadata.folderId`.

### Recursive listings

`recursive` is `true` for a `list` that also covers every folder below
`folder`: a [`dbObjectSource`](/docs/db/api#browser) search, and a flat
listing (no `folderId`), which reads the whole scope and arrives as a
recursive listing of the root.

A rule that hides a folder from `list` must also cover a recursive listing
of any folder above it. To keep listings to one folder, return `false` when
`recursive` is set, and pass
`dbObjectSource(api.db, { recursiveSearch: false })` so search stays in the
open folder instead of failing with `FORBIDDEN`.

## Route options

Set per-route options under `plugins: { db: … }`:

```ts title="lib/s3.ts"
routes: {
  // One key per user: a new upload replaces the old avatar instead of
  // failing with OBJECT_EXISTS. `requireUserId` is your auth helper.
  avatar: route({
    upload: {
      fileTypes: ["image/*"],
      object: async ({ request }) => ({
        key: `${await requireUserId(request)}/avatar`,
      }),
    },
    download: true,
    plugins: { db: { replace: "overwrite" } }, // [!code ++]
  }),
  // Not tracked: no rows, no ownership checks.
  public: route({
    upload: true,
    download: { guard: requireAdmin },
    plugins: { db: false }, // [!code ++]
  }),
},
```

- `replace: "overwrite"` lets an upload replace an active object at the same
  key. Without it, that upload fails with `OBJECT_EXISTS` (`409`). The row
  stays active until the new upload is confirmed: see
  [Overwrites](/docs/db/lifecycle-hooks#overwrites).
- `false` turns off tracking and every db hook for the route, and its upload
  tickets are not bound to a scope. When such a route enables download or
  delete with no route or feature guard, the plugin logs a warning at
  startup: nothing then checks who owns the object.

## Delete behavior

Deletes go through the normal server delete path: `delete` on `s3.api` or
the browser client, [`useDelete`](/docs/react/hooks/delete), or the
[`Delete`](/docs/ui/components/delete) component. `s3.db.objects` has no
delete method: it never touches S3.

The server removes the object with `DeleteObject`. The plugin then aborts a
multipart upload in flight on the key, and updates the row by `deleteMode`:

| `deleteMode`       | S3 object           | Database row                                     |
| ------------------ | ------------------- | ------------------------------------------------ |
| `"soft"` (default) | permanently deleted | kept as `status: "deleted"` with `deletedAt` set |
| `"hard"`           | permanently deleted | removed                                          |

```ts
db({
  client: dimahS3Db,
  resolveScope,
  deleteMode: "hard", // [!code ++]
});
```

- Listings hide soft-deleted rows by default. Soft delete is a history
  record, not a recycle bin: the file is gone from S3.
- Use `"hard"` when every delete must also erase the row (for example,
  GDPR-style erasure). To keep deleted rows for a while, run
  [`pruneDeleted`](/docs/db/purge#prune-deleted-rows) from a job.
- A `pending` row whose object never landed (a closed tab, a network error)
  is deleted the same way, so it stops counting toward the
  [quota](/docs/db/api#quota) before [purge](/docs/db/purge) runs.
- Deleting a soft-deleted object again succeeds, like a plain S3 delete. A
  key with no row is `OBJECT_NOT_FOUND`: its owner cannot be checked.

## PostgreSQL schema

To keep the tables in a PostgreSQL schema, such as `storage`, create the
client from `DimahS3Db.names.schema("storage")`, and generate with the same
client:

```ts title="lib/dimah-s3-db.ts"
export const dimahS3Db = DimahS3Db.names
  .schema("storage")
  .client(drizzleAdapter({ db, provider: "postgresql" }));
```

- `migrate` creates the schema.
- The generated Drizzle file exports it as `storageSchema`, so `drizzle-kit`
  creates it too.
- The generated Prisma models carry `@@schema("storage")`. List it in the
  datasource, as in `schemas = ["public", "storage"]`.
- FumaDB keeps its settings table, `private_dimah_s3_settings`, in the
  search path.

## CLI

`runCli` runs the FumaDB CLI for the `@dimah-s3/db` schema:

```ts title="scripts/dimah-s3.ts"
import { runCli } from "@dimah-s3/db/cli";
import { dimahS3Db } from "@/lib/dimah-s3-db";

await runCli(dimahS3Db);
```

```bash
npx tsx scripts/dimah-s3.ts generate latest -o db/dimah-s3.ts
npx tsx scripts/dimah-s3.ts migrate latest
```

| Command                     | Does                                                                                                                                    |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `generate latest -o <file>` | Writes the Drizzle tables or Prisma models for the client's adapter, or with Kysely the SQL that creates the tables                     |
| `migrate latest`            | Creates the tables with the Kysely adapter. From code, `migrate(client)` does it, and also refuses a database at another schema version |

With Drizzle and Prisma, `generate` does not connect to the database, so
the adapter can take `db: undefined` or `prisma: undefined`.

The schema declares these indexes, so `migrate`, `drizzle-kit`, and Prisma
Migrate create them:

| Index                                 | Table            | Columns                                      |
| ------------------------------------- | ---------------- | -------------------------------------------- |
| `storage_object_bucket_key_uk`        | `storage_object` | `bucket`, `key` (unique)                     |
| `storage_object_scope_folder_idx`     | `storage_object` | `scope`, `status`, `folder_id`, `created_at` |
| `storage_object_scope_updated_idx`    | `storage_object` | `scope`, `status`, `updated_at`              |
| `storage_object_scope_name_idx`       | `storage_object` | `scope`, `status`, `search_name`             |
| `storage_object_scope_size_idx`       | `storage_object` | `scope`, `status`, `size`                    |
| `storage_object_status_expires_idx`   | `storage_object` | `status`, `expires_at`                       |
| `storage_folder_scope_path_idx`       | `storage_folder` | `scope`, `path`                              |
| `storage_folder_scope_parent_name_uk` | `storage_folder` | `scope`, `parent_id`, `name` (unique)        |

On MySQL, `key` and `path` are indexed on their first 512 characters, and
`search_name` on its first 255. Two keys in one bucket that share their
first 512 characters count as the same key.

## API Reference

### DbPluginOptions

The options of `db()`.

| Prop           | Type                                                      | Default  | Description                                                                                    |
| -------------- | --------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------- |
| `client`       | `DimahS3DbClient`                                         | required | `DimahS3Db.client(adapter)`                                                                    |
| `resolveScope` | `(context: ScopeContext) => string \| null \| Promise<…>` | required | Owner scope of the caller, at most 255 characters; `null` rejects the call with `UNAUTHORIZED` |
| `getSession`   | `(request: Request) => TSession \| Promise<TSession>`     | —        | Loads the session that `resolveScope`, `authorize`, and `quota` see; once per `Request`        |
| `authorize`    | `(context: AuthorizeContext) => boolean \| Promise<…>`    | —        | Narrows access after the ownership check; `false` rejects the call with `FORBIDDEN`            |
| `quota`        | `DbQuota \| (context) => DbQuota \| null \| Promise<…>`   | —        | Byte, file, and folder caps per scope ([Quota](/docs/db/api#quota))                            |
| `deleteMode`   | `"soft" \| "hard"`                                        | `"soft"` | Keeps a `deleted` row, or removes it                                                           |
| `attributes`   | `DbAttributesOptions`                                     | —        | Enables `attributes` on `PATCH /db/object` ([Attributes](/docs/db/api#attributes))             |

### DbRouteOptions

Set on a route as `plugins: { db: … }`. `false` turns tracking off for the
route.

| Prop      | Type          | Default | Description                                                                        |
| --------- | ------------- | ------- | ---------------------------------------------------------------------------------- |
| `replace` | `"overwrite"` | —       | Lets an upload replace an active object at the same key instead of `OBJECT_EXISTS` |

### ScopeContext

What `resolveScope` and a `quota` function receive. A `quota` function also
gets the resolved `scope`.

| Property    | Type             | Description                                                                                                                          |
| ----------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `request`   | `Request`        | The incoming request, or a synthetic one for in-process calls                                                                        |
| `locals`    | `DimahS3Locals`  | Locals the guards have set so far                                                                                                    |
| `session`   | `TSession`       | The `getSession` result, resolved once per request; `undefined` without `getSession`                                                 |
| `operation` | `ScopeOperation` | What the scope is resolved for ([Scope](#scope))                                                                                     |
| `route`     | `string`         | Named route of the call. `list` has one only when the client filters by route; `read`, `update`, and the folder operations have none |

### AuthorizeContext

Every `ScopeContext` field, plus:

| Property         | Type                                                   | Description                                                                                  |
| ---------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| `scope`          | `string`                                               | The resolved scope                                                                           |
| `key`            | `string`                                               | Object key; absent on `list` and the folder operations                                       |
| `folder`         | `string \| null`                                       | Where the target is now, as a folder path; `null` is the root                                |
| `folderId`       | `string \| null`                                       | Id of the folder `folder` names; `null` is the root                                          |
| `destination`    | `{ folder: string \| null; folderId: string \| null }` | Where a move or a new folder puts the target                                                 |
| `recursive`      | `boolean`                                              | `true` when a `list` also covers every folder below `folder`                                 |
| `clientMetadata` | `Record<string, string>`                               | Client extras of the upload; set on `upload` only                                            |
| `object`         | `StorageObject`                                        | The stored row, when the call targets one, including the active object an overwrite replaces |

## Frequently asked questions

<Accordion title="Does s3.put create a row?">

Yes. `s3.put` runs the same hooks with `kind: "server"`. Pass the caller's
`request` (or trusted `locals`) so `resolveScope` knows who it is, and
`clientMetadata.folderId` to file it in a folder that already exists:

```ts
const folderId = "…"; // id from createFolder

await s3.put(
  {
    route: "files",
    name: "report.csv",
    type: "text/csv",
    body: csv,
    clientMetadata: { folderId },
  },
  { request },
);
```
